### 1. Тормозной старт и лишний loading

Проблема:

- сейчас первый экран может висеть на loader несколько секунд;
- для небольшого проекта это слишком долго;
- у пользователя создается ощущение, что приложение зависло.

Что нужно сделать:

- убрать тяжёлый blocking loading на главном экране;
- показывать shell UI сразу;
- данные подгружать асинхронно, без полного скрытия экрана;
- если нужно, использовать skeleton вместо пустого spinner-only экрана;
- не блокировать весь экран ради fetch трех API;
- не ждать лишние запросы до первого рендера, если они не критичны.

Что важно:

- дизайн должен появляться сразу;
- шапка, навигация и основная рамка должны быть видны без задержки;
- loading можно оставить только внутри отдельных блоков;
- spinner на весь экран допустим только на очень короткий момент.

Практическая цель:

- убрать ощущение “зависло”;
- сократить время до первого полезного отображения;
- не менять визуальный стиль.

## Почему сейчас загрузка слишком долгая

По текущему коду причина выглядит не как “большой проект”, а как архитектурный loading-path:

1. Главный экран ждёт несколько fetch-запросов перед полным показом UI.
2. Если `loading === true`, весь экран скрывается и показывается только spinner.
3. Это делает маленькое приложение визуально медленным, даже если сервер уже отвечает быстро.
4. Для небольшого проекта такое поведение не нужно.

Что надо изменить по смыслу:

- не прятать весь экран;
- рендерить shell сразу;
- данные подменять по мере прихода;
- заменить full-screen spinner на локальные skeletons;
- не делать критический путь зависимым от всех API сразу;
- если часть данных недоступна, показывать пустое состояние, а не полный блокирующий loader.

Правило для агента:

- если экран можно показать без данных, показывай его сразу;
- если нужен loader, он должен быть маленьким и локальным;
- never block the whole page unless это реально вход в систему.

## Как сохранить дизайн без изменений

Дизайн должен оставаться тем же, что уже принят в проекте:

- светлый, дружелюбный, премиальный;
- синие CTA;
- золотые stars;
- мягкие тени;
- скругления 24-32px;
- без случайной смены визуального языка.

Правила:

1. Не менять палитру без причины.
2. Не уводить проект в тёмную тему.
3. Не делать “корпоративный” UI.
4. Не перепридумывать карточки, если существующий паттерн уже работает.
5. Не убирать hero-стиль и ощущение “детского квеста”.
6. Если надо добавить новые элементы, повторять уже существующие размеры, ритм и скругления.

## Стабильный маршрут локальной проверки

Для этого проекта стабильнее проверять не через бесконечный `next dev`, а так:

1. `npm run build`
2. `npm run start -- --hostname 127.0.0.1 --port 3000`
3. открыть главную и соседние вкладки
4. проверить переходы между `/`, `/schedule`, `/grades`, `/settings`

Почему так:

- `next dev` в этом проекте уже показал нестабильность с потерянными чанками;
- production preview через `next start` ближе к Vercel;
- если production preview чистый, то проблема обычно именно в dev-caching, а не в самом приложении.

### Если снова всплывает ошибка вида `Cannot find module './XXX.js'`

Тогда порядок такой:

1. остановить dev/start сервер;
2. удалить `.next`;
3. заново выполнить `npm run build`;
4. запустить `npm run start`;
5. только потом проверять переходы;
6. если нужно менять маршруты, не трогать одновременно дизайн и runtime-обвязку.

### Обязательные route-fallback файлы

Чтобы переходы не роняли экран в белый шум, у корня должны быть:

- `app/loading.tsx`
- `app/error.tsx`
- `app/not-found.tsx`

Их задача:

- сохранить общий визуальный каркас;
- не давать пустой белый экран;
- не ломать ощущение, что проект “живой” даже при подгрузке или ошибке.

### Навигационный паттерн

- `Link` должен быть `Link`, без вложенного `button`;
- активная вкладка должна подсвечиваться через класс;
- layout и navigation должны быть общими для всех child pages;
- любые новые страницы должны повторять текущий shell-паттерн, а не придумывать свой.

### Parent login guard rule

- `middleware` не должен защищать `/parent/login`;
- защищать нужно только `/parent` и вложенные приватные роуты, но не экран входа;
- если login попал под защиту, будет redirect loop и `ERR_TOO_MANY_REDIRECTS`;
- для parent flow всегда проверять, что login открывается без cookie, а `/parent` без cookie уводит на login ровно один раз.
