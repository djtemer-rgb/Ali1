## 3. Канон, который уже согласован с пользователем

Ниже не обсуждать заново. Это уже принято.

### 3.1. Кнопка в “Послании героя”

В модалке hero message:

- было: `Понятно!`
- должно стать: `Хорошо!`

### 3.2. Тумблер с условиями

Название тумблера:

- `Требовать выполнить условия`

Не `Требовать открыть условия`.  
Не `Требовать выполнить усилия`.

### 3.3. Поведение recurring-задачи при правке в тот же день

Если родитель изменил recurring-задачу в тот же день:

- **невыполненная** today-задача должна обновиться сверху;
- **выполненная** today-задача не должна переписываться задним числом.

### 3.4. Если у recurring-задачи убрали сегодняшний день

- если today-задача ещё не выполнена, убрать её из активного today-списка;
- если уже выполнена, не ломать историю и не пересчитывать задним числом результат дня.

### 3.5. Разовая задача

Если задача создаётся **без дней недели**, это означает:

- задача разовая;
- она должна идти в today tasks;
- она не должна отображаться как recurring item в “Расписании”.

Если потом такую задачу снова включают `ON`:

- она должна заново стать активной задачей **на сегодня**.

### 3.6. Нижний блок выключенных задач

В настройках нужен отдельный нижний collapsible-блок для:

- всех задач `OFF`;
- всех выполненных разовых задач, которые автоматически становятся `OFF`.

Правила:

- новые упавшие вниз задачи должны быть **наверху** нижнего списка;
- внизу не нужны стрелки порядка;
- там нужен вертикальный скролл;
- желательно видимая высота примерно на 5 элементов;
- нужна общая кнопка очистки `Удалить всё` / `Очистить неактивные` через кастомную модалку.

### 3.7. Верхний блок активных задач

Верхний список в настройках:

- только активные задачи;
- ручной порядок стрелками вверх/вниз;
- сколько задач есть, столько и показывать, а не искусственно три штуки;
- выполненные разовые, которые уже стали OFF, сверху мешаться не должны.

### 3.8. Предметы

Не drag-and-drop.  
В этой итерации:

- компактные стрелки вверх/вниз;
- порядок должен сохраняться;
- этот же порядок должен использоваться в выпадающем списке оценок.

## 5. ИТЕРАЦИЯ 1 — Tasks / Schedule / Active-Inactive Architecture

### 5.1. Цель итерации

Привести механику шаблонов, today-задач, OFF/ON и настроечного списка к одной понятной модели, чтобы дальше уже не лечить симптомы.

### 5.2. Что именно должно получиться после итерации

После этой итерации должно быть так:

- recurring templates живут как шаблоны;
- они показываются в “Расписании” без чекбоксов выполнения;
- в нужный день recurring template поднимается наверх в today tasks;
- today task остаётся отдельным дневным instance;
- изменение recurring template обновляет невыполненный today instance;
- выполненный today instance задним числом не ломается;
- разовые задачи живут отдельно от recurring schedule logic;
- OFF/ON работает и в настройках, и в today flow;
- completed one-time задачи автоматически архивируются в нижний OFF-блок настроек.

### 5.3. Конкретные изменения по данным и логике

#### 5.3.1. Templates

В `app/api/tasks/templates/route.ts` и связанных типах:

- сохранить текущую модель templates;
- не ломать существующие данные;
- мягко расширить template при необходимости дополнительными полями:
  - `inactiveAt`
  - возможно `sortOrder` или использовать текущий порядок массива, если это уже основной механизм;
- не внедрять тяжёлую миграцию, если можно обойтись backward-compatible normalizer.

#### 5.3.2. Day tasks

В `app/api/tasks/day/route.ts`:

- оставить `templateId` как основную ссылку на источник;
- доработать reconcile так, чтобы:
  - если task не completed, её поля подтягиваются из текущего template;
  - если task completed, контент task не переписывается;
  - subtasks merge для completed не должен ломать уже зафиксированный результат;
  - если recurring template больше не актуален на сегодня и task не completed, task должен исчезнуть из today active state;
  - если recurring template больше не актуален на сегодня, но task completed, task остаётся как дневной факт.

#### 5.3.3. One-time задачи

Нужно чётко разделить:

- recurring template: есть `repeatDays.length > 0`
- one-time task: `repeatDays.length === 0`

One-time правила:

- не отображать её в главном блоке “Расписание”;
- при создании без дней недели сразу делать её задачей на текущий день;
- после выполнения автоматически переводить template в `active: false`;
- помечать `inactiveAt`;
- в настройках уводить её в нижний блок OFF.

#### 5.3.4. OFF / ON

Если родитель нажал OFF:

- задача должна реально уйти из активного потока;
- recurring невыполненная задача должна перестать показываться ребёнку;
- one-time задача тоже должна реально выключаться, а не просто визуально менять label.

Если OFF -> ON:

- recurring возвращается в активные templates и снова участвует в schedule logic;
- one-time возвращается в активные и получает сценарий “снова на сегодня”.

### 5.4. Конкретные изменения по интерфейсу

#### 5.4.1. Главная страница `app/page.tsx`

В блоке “Расписание”:

- убрать механику завершения через schedule row;
- расписание — только read-only представление шаблонов;
- показать:
  - title
  - stars
  - category
  - статус `На сегодня` / `Завтра` / `Выполнена сегодня`
  - ближайший день / дату
- разовые задачи там не показывать.

#### 5.4.2. Настройки `app/settings/page.tsx`

Разделить шаблоны на два списка:

1. **Активные**
   - только `active === true`
   - ручной reorder стрелками
   - без искусственного лимита “три карточки”

2. **Неактивные / выполненные разовые**
   - collapsible блок
   - `active === false`
   - сортировка по `inactiveAt` desc
   - без стрелок порядка
   - с кнопкой массовой очистки

### 5.5. Что агент обязан проверить в интернете в этой итерации

- лучшие практики хранения “template + daily instance”;
- поведение повторяющихся задач при редактировании уже существующих instances;
- community-подходы, как не ломать completed historical entries.

### 5.6. Проверка окончания итерации

Нужно вручную проверить:

1. recurring задача с Пн/Ср/Пт в воскресенье показывает “на завтра”, а не active today;
2. с наступлением нужного дня recurring появляется сверху;
3. при переименовании recurring снизу наверху меняется название, если задача не выполнена;
4. completed recurring не ломается после редактирования шаблона;
5. one-time задача не появляется в расписании;
6. OFF реально выключает задачу;
7. completed one-time уходит в нижний OFF-блок;
8. ON возвращает её в активные и снова создаёт на сегодня;
9. нижний блок показывает последние ушедшие вниз первыми.

## 6. ИТЕРАЦИЯ 2 — Child Task UX / Subtasks / Confirm Modals

### 6.1. Цель итерации

Сделать детское поведение задач предсказуемым и мягким, без лишнего тыканья, и убрать browser-native confirm из flow отмен.

### 6.2. Канон поведения child task

#### 6.2.1. Если у задачи нет подзадач

- обычный тап по внешнему чекбоксу завершает задачу.

#### 6.2.2. Если у задачи есть подзадачи, но не требуется обязательное выполнение условий

Первый тап:

- открывает модалку;
- ребёнок видит условия/подзадачи;
- есть понятная мягкая кнопка подтверждения, что он увидел условия.

После первого открытия:

- при следующем тапе по внешнему чекбоксу задача должна завершаться;
- не заставлять ребёнка каждый раз проваливаться внутрь, если обязательного требования нет.

Если задача может завершаться прямо из модалки безопасно, это допустимо, но итоговый UX должен быть максимально простым для ребёнка.

#### 6.2.3. Если включён режим `Требовать выполнить условия`

Пока все checkbox-подзадачи не завершены:

- внешний чекбокс не завершает задачу;
- внешний чекбокс только повторно открывает модалку.

Когда ребёнок отмечает **последнюю** обязательную подзадачу:

- основная задача должна завершаться **сразу внутри модалки**;
- без требования выйти наружу и нажать ещё раз.

### 6.3. Тексты и микрокопирайт

Для ребёнка тексты должны быть:

- короткими;
- мягкими;
- понятными.

Нужно явно подсказать смысл:

- что тут сначала надо выполнить условия;
- что задача завершится после выполнения всех обязательных шагов.

### 6.4. Конкретные изменения

#### 6.4.1. `app/components/TaskCard.tsx`

Нужно:

- аккуратно развести логику:
  - `requiresOpenDetails`

  - состояние `detailsOpened`

Если понадобится, ввести более явное состояние вроде:

- “условия уже были показаны”;
- “можно завершать без повторного открытия”;

#### 6.4.2. `app/settings/page.tsx` + task form

#### 6.4.3. Hero modal button

### 6.5. Что агент обязан проверить в интернете в этой итерации

- лучшие UX-паттерны для task + subtasks flow;

### 6.6. Проверка окончания итерации

1. Задача без subtasks завершается сразу.
2. Задача с subtasks без обязательного режима:

#### 7.2.5. Default prompts

Нужно встроить default values так, чтобы:

- при первом запуске textarea не были пустыми;
- пользователь мог их потом редактировать.

Base prompt по смыслу:

- 65–115 слов максимум;
- не однообразный;
- не долбить героями каждый раз;
- хвалить усилие, дисциплину, честность, самоуправление;
- иногда мягко напоминать про границы и право сказать “нет” плохому.

Deep prompt:

- добавляет один смысловой слой;
- не делает текст сильно длиннее;
- чередует темы: внутренняя сила, дисциплина, честность, границы, ошибки как тренировка, осознанность.

### 7.5. Web Push

#### 7.5.1. Что надо исправить

Нужно не просто убрать ошибку, а довести сценарий до понятного рабочего состояния:

- если нет `NEXT_PUBLIC_VAPID_PUBLIC_KEY`, статус должен быть понятным;
- в UI родителю нужно коротко объяснить, что без public key web push не подключится;
- включение/выключение должно реально сохраняться;
- подписка должна реально отправляться на backend.

#### 7.5.2. Что нужно зафиксировать по env

Нужны env:

- `NEXT_PUBLIC_VAPID_PUBLIC_KEY`
- `VAPID_PRIVATE_KEY`
- желательно `VAPID_SUBJECT`

Важно:

- `NEXT_PUBLIC_VAPID_PUBLIC_KEY` — клиентская переменная;
- в Next.js она вшивается в bundle на **build-time**;
- после изменения нужен новый build/redeploy.

#### 7.5.3. Что написать в короткой инструкции для родителя/разработчика

Нужно кратко зафиксировать:

1. VAPID keys генерируются один раз библиотекой `web-push`.
2. Public key идёт в `NEXT_PUBLIC_VAPID_PUBLIC_KEY`.
3. Private key идёт в `VAPID_PRIVATE_KEY`.
4. Private key никогда не отдавать в браузер.
5. После добавления public key нужно заново пересобрать/задеплоить проект.
